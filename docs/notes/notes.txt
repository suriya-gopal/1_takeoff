Views built (trips/views.py):
- trip_manual_view  -> FBV, HttpResponse (manual loader.get_template) -> /trips/manual/
- trip_list_view    -> FBV, render() shortcut                        -> /trips/
- TripDetailView    -> CBV, base django.views.View, get() implemented -> /trips/<pk>/
- TripListView      -> CBV, generic ListView, filtered to public trips -> /trips/generic/

All four built against Trip since it's the model everything else (stops, items,
join requests) hangs off - one model, four ways of rendering it.

Reflection (bonus):
- HttpResponse (manual) forces you to think about what render() normally hides -
  loading the template object yourself makes it obvious that render() is just
  "get_template + .render() + wrap in HttpResponse" in one call.
- Base View vs generic ListView: base View was worth it for TripDetailView, which
  needed two related querysets (stops AND join_requests) in one context - ListView's
  single queryset model doesn't fit that naturally. ListView earned its keep on the
  plain "list of public trips" page, where there's nothing beyond the one queryset.

Settings split into base/development/production (takeoff/settings/{base,development,production}.py
+ secrets_environment.py using django-environ). SECRET_KEY moved out of source into .env.

SEARCH, FORMS, CHART, STATIC FILES AND API

--- URL linking and get_absolute_url() ---------------------------------------
Trip.get_absolute_url() returns reverse("trips:trip-detail", kwargs={"pk": self.pk}).
It is useful for every feature that has to point at ONE trip:
  * Home / All-trips / Community cards      -> {{ trip.get_absolute_url }}
  * search results (filter and budget)      -> same call, so links never drift
  * "Plan your trip" form                   -> after a valid submission, CreateView
    redirects to the new trip automatically because success_url is not set
  * "Request to join"                       -> redirect back to the trip page
  * the JSON API                            -> every result carries its "url"
If the route ever changes (e.g. /trips/<pk>/ -> /trips/<slug>/), only the model
method changes; no template needs editing.
Flow: models.py (get_absolute_url) -> urls.py (name "trip-detail") -> views.py
(TripDetailView) -> templates/trips/trip_detail.html.

--- Search: GET vs POST (design thinking) -------------------------------------
GET  (filter by destination / country / date / Planned-Completed tab)
  Same link -> same results, so it is bookmarkable and shareable. Only PUBLIC
  trips are searched this way, because a link can be passed around.
POST (budget + group size, from the Trip Input screen's budget range / group size)
  Budget is personal, so it goes in the request body instead of the URL, browser
  history and server access logs. Trade-off: no shareable result link, and a
  browser refresh asks to re-submit. (POST hides data from the URL; it is not
  encryption. Use HTTPS when deployed.)
Relationship spanning used: Trip -> TripStop -> Destination
  (stops__destination__name__icontains, stops__destination__country).
Summaries: Trip.count(), public count, JoinRequest count (totals);
  Destination.annotate(Count("stops__trip", distinct=True)) and
  JoinRequest.values("status").annotate(Count(...)) (grouped).
distinct=True / .distinct() are needed because joining across stops can repeat a trip.

--- Static files ----------------------------------------------------------------
Organisation choice: site-wide CSS lives in ONE project-level folder,
takeoff/ui-ux/static/css/ (normalize.css + our own style.css), registered with
STATICFILES_DIRS. The logo stays in the app (trips/static/trips/img/logo.png),
because an image the app owns belongs with the app and is namespaced under trips/.
The earlier inline <style> block was moved into style.css; colours come from the logo.
Cache busting, two layers:
  1. Development: base.html appends ?v={% now "U" %} (a timestamp) to the CSS URLs,
     so the browser re-downloads after every edit. Downside: it defeats caching
     completely, so it is a development trick only.
  2. Production: ManifestStaticFilesStorage (takeoff/settings/production.py).
     `collectstatic` renames style.css -> style.<hash>.css; a changed file gets a
     new URL. Verified: static('css/style.css') -> /static/css/style.39548259077b.css.
     Django 5.1+ removed the old STATICFILES_STORAGE setting; the STORAGES dict is
     its replacement. Before deploying, delete the ?v={{ ts }} part so production
     caches properly.

--- Chart -------------------------------------------------------------------------
Chart data = destination_popularity() (database query). The PNG is drawn into a
BytesIO (a file held in RAM), never written to disk. RAM implications: the Figure
holds pixels while drawing, so plt.close(fig) is required or figures pile up per
request; the finished PNG is tens of KB. Every page view draws the chart again -
if traffic grew, cache it.

--- API plan ------------------------------------------------------------------------
How the API will grow: the read-only endpoints are the first step. Next steps are
authentication (so owners can see their own private trips), then write endpoints
(create trip, request to join, accept/decline) that reuse the same forms and validation.
Data served now: PUBLIC trips only (title, dates, route, budget range, seats open,
owner display name + verified flag, url), and destinations with public-trip counts.
Never served: private trips, e-mail addresses, join-request messages.
Data planned later: itinerary items / booking links for public trips, community
completed-trip memories (photos, ratings), popular-destination feeds for recommendations.
